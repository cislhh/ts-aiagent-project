## 0. 方法与引用约定

### 1.3 文风解剖

**四个可以直接复用的特征**（这是资产，不要丢）：

1. **第一人称 + 具体场景开场**，不写"随着互联网的发展"。例：《KeepAlive》开篇即"需求很朴素：列表页点项目名称跳到详情页，办完事点返回，筛选条件、分页页码、当前 tab 全部保留"（`cuiji-blog/data/blog/myNewBlog/Vue3-KeepAlive-缓存机制深入与实战踩坑.mdx:12`）。
2. **表格做对照**是作者的签名手法，且用得对：《KeepAlive》用三行表穷举"包 div / 包子组件 / 布局层包 RouterView"三种放法的结局；《三份合同》用三行表把 description / parameters / 返回值拆成三份合同。
3. **引官方原文当锚点再拆解**，而不是转述。例："官方文档第一句：`<KeepAlive>` 是一个内置组件，它的功能是在多个组件间动态切换时**缓存被移除的组件实例**" —— 然后咬住"组件实例"四个字往下推（同文件 `:18–22`）。
4. **追问到机制层**：为什么包 div 无效 → 因为 KeepAlive 要拿到子节点的组件 vnode 才能按 type 做缓存 key（同文件 `:41`）。这是"架构判断"能力的证据。

**三个会拖后腿的习惯**（与新定位冲突，成稿时要有意识地改）：

1. **"一、二、三 + 是什么/为什么/怎么做"的通用骨架**在 2025 年那批里是模板化的（3、5、11、12 四篇尤其明显），读起来是资料汇编，不是判断复盘。
2. **几乎没有自我否定段**。20 篇里只有《KeepAlive》和《Lenis》明确写了"我先试了 X，错了"。而"单点决策复盘"的支点恰恰是"我当时怎么想的、错在哪"。
3. **代码块密度与"不写代码级知识"直接冲突**：《Web Components》24 个代码块、《TypeScript 高级类型》20 个、《微前端》23 个。新定位下单个代码块的上限应该压到 3–5 个，且只贴"能证明判断"的那几行。

### 1.4 与「单点决策复盘」的差距诊断

现有文章回答的是"这个机制是什么、怎么用"；新定位要回答的是"**在几条都说得通的路里，为什么走这条，代价是什么，后来哪里痛**"。

差距不在素材量，在**叙述配比**：把"是什么/怎么做"压到 1/3，把"当时有哪几条路 / 为什么砍掉另外两条 / 事后哪里应验了"提到 2/3。已有的 20 篇里，《KeepAlive》和《Lenis》已经摸到了这个配比（先给需求、再给三种试法的结局、最后给结论），可以直接当文风模板。

## 4. 三个系列方向

### 系列 A｜AI 协作复盘：谁在做判断

**定位**：每篇一个"AI 干完了、人被坑了、判断拧回来了"的具体回合。落点是**判断标准**（什么算过、什么算没过、怎么让标准不漂移），不是 prompt 技巧。
**目标读者**：已经在用 Claude Code / Cursor 写业务代码，但说不清"我到底在管什么"的前端。
**不写什么**：prompt 模板、"如何让 AI 更听话"、工具横评。

| 选题 | 一句话命题 | 素材 |
| --- | --- | --- |
| 我让 AI 教我一门新技术，它被我否了七次 | 你说过的约束，模型不会自动遵守；约束必须变成产物结构 | S1 |
| 我把 agent 的记忆搬出了它的脑袋 | 状态要能被脚本读，不能只被人记 | S2 |
| AI 说"我刚查过了" | 模型对"我验证过"的自述不可信，只信当场跑出来的输出 | S10 |
| AI 给我 13 条优化建议，我砍掉了 3 条 | 建议是对的，但优先级是人的责任 | S8 |
| 同一份规则存了三份，它就一定会漂移 | 副本 = 漂移，这是 AI 协作的熵增定律 | S1 拆出的单点 |

### 系列 B｜架构取舍：线画在哪

**定位**：不写"什么是 X"，只写"这条线为什么画在这里、画错的代价是什么"。
**目标读者**：从 Vue/React 单页应用走过来、第一次要做"有后端"的产品的前端。
**不写什么**：微前端/DDD/分层架构的名词解释（博客 #11 已有微前端长文）。

| 选题 | 一句话命题 | 素材 |
| --- | --- | --- |
| 前端别直接连数据库 | 先划运行时与数据边界，再进业务模块 | S6 |
| 周任务撑不住的时候，我重写了模型 | 数据模型改不动，通常是业务先变了，不是代码烂 | S5 |
| Agent 的每一步都该有人点头 | 有副作用的动作，审批应该在架构里，不在 prompt 里 | S9（需切到审批层） |
| 哪些东西是"故意不做"的 | 明确写下推迟项，比写满功能清单更能证明架构想过 | S6 的"deliberate deferrals" |

### 系列 C｜业务与性能的账

**定位**：所有结论都要有数字或算式。不谈"更快了"，谈"从多少到多少、代价是什么"。
**目标读者**：要为自己提的优化方案负责、会被问"收益多少"的人。
**不写什么**：API 用法清单、性能指标科普。

| 选题 | 一句话命题 | 素材 |
| --- | --- | --- |
| 一份简历我存了两遍 | 存储优化的第一步不是压缩，是去重 | S4 |
| 登录切不了账号：三个默认值叠出来的 bug | 排查顺序应该从"谁在替我记住状态"开始 | S7 |
| 13 条性能问题里，哪几条是给自己找事 | 优化清单要按"是否在关键路径"排序，不是按严重度标签 | S8 |
| 图片加载：先解耦服务，再谈格式 | 格式优化是最后一公里，服务解耦才是第一公里 | 博客 #4 换角度重写 |

## 5. 第一篇样板的 3 个首选

筛选标准：优先"AI 写代码/写内容、但靠人的判断救回来"；其次要求**脱敏成本低**（不碰公司代码）、**素材可验证**（有日期、有原文、有数字）、**能立住"高阶"人设**（讲判断而不是讲 API）。

### 首选 1｜S1《我让 AI 教我一门新技术，它被我否了七次》★ 建议作为开号第一篇

**为什么是它**：这是全部素材里唯一同时具备五个条件的——AI 生成量极大（623 行讲义 / 14 道题）、人的判断真的扭转了结果、回合可数（三次否决 → 第五次追问 → 第七次才挖到根因）、根因可验证（规则有 3 份副本）、零公司代码。而且它天然回答"AI 时代前端的技术性在哪"——在定义什么叫"合格"。

**叙事骨架（建议五段）**：

1. **场景**：我要 12 周从 Vue/React 转成能独立交付 AI 应用，于是让 agent 每 2 天自动推一课。
2. **第一版交付物有多"完整"**：623 行讲义、4 个知识点、14 道题、4 篇必读文档 —— 全部合规，全部没用。
3. **三次否决**：看不懂这节要干什么 → 不知道 4 篇文档该看哪几节 → 载体错了（我要的是图形化 HTML，不是 md 教案）。每次否决都变成一条硬规则。
4. **转折**：我反问"你是不是根本没执行那个 teach skill"。它去核实，结论是"是，一条都没执行"。
5. **终点不是修好这一课，是修掉"会反复坏"的地方**：为什么同一个问题会反复出现？因为教学法同时存在于三个地方（笔记、自动化任务描述、项目记忆），改了一处另两处还在发号施令。于是抽成单一出处 + 建了一个零依赖的交付前闸门（`tools/lesson-check.mjs`，280 行，检查跳步、过期版本号、讲解被折叠等 10 类问题）。**人的判断最后变成了机器能执行的规则——这才是我认为 AI 协作的正解。**

**需要作者补的口述素材**：

- 你当时为什么第一反应是"你是不是没用那个 skill"，而不是"再来一版"？（这个直觉从哪来）
- 三次否决里，哪一次你最想放弃？当时有没有想过"算了，我自己写"？
- 回看这七轮，有没有一条要求其实是你自己一开始没想清楚，后来才想明白的？（有的话，这篇的诚实度会翻倍）
- 课最后救回来了吗？救回来的标志是什么（某一课你一次就通过了？还是你再也没提过意见？）
- 那个闸门现在拦下过什么？有没有一次是它拦对了、你本来要发出去的？

**风险与处理**：原文里有对 agent 的直白批评（"你不告诉我这节课应该干什么…那还需要老师干什么"）。成稿建议改成"我的要求没有被满足"，把矛头从工具转向**约束的表达方式**，否则读者容易读成"作者在骂 AI"，反而削弱"人的判断"这个主题。

### 首选 2｜S2《我把 agent 的记忆搬出了它的脑袋》

**为什么是它**：机制可复用、有代码但只需要讲结构、自带一个绝妙反例（AI 写的校验器骗了 AI）。写完可以成为系列 A 的地基文，后面每篇都能引用它。重叠度低，且完全避开公司信息。

**叙事骨架**：

1. 每轮自动化任务都是全新对话 —— 它不记得讲到第几课。
2. 第一反应是"把状态写进 prompt"，失败：prompt 会膨胀，而且一样会漂移。
3. 于是把记忆搬到文件系统：台账（唯一事实来源，41 行一课一行）、只追加的日志（每条结尾必须有完成标记）、校验脚本（每轮第一件事是跑它拿事实，而不是回忆）。
4. 加上状态机（未开课 → 已发简报 → 已提交 → 已批改 → 已掌握，另有需重学）、发新课闸门（同时最多挂 1 节）、自愈规则（上轮没写完成标记 → 本轮先修再推进）。
5. **反例**：校验器判断"上轮是否跑完"时用了定长截断（只看正文前 800 字符），长条目会把结尾的完成标记切到窗口外，于是在**刚跑完的那一轮**就误报"上轮炸了"，让下一轮白跑一趟自愈。改成"按下一个标题界定正文边界"才修好——并且在代码里留注释禁止改回定长截断。
6. **结论**：agent 的记忆不该是"它记得"，而该是"它读得到"；而且读得到的东西必须有一个不会被自己骗过的校验器。

**需要作者补的口述素材**：

- 误报那次你是怎么发现的？是看日志、还是被结果恶心到了才回头查？
- 如果没有校验器，最坏会怎样？能不能举一次真实的"重复推进/漏推进"？
- 这套台账现在有几行？维护它本身花了多少时间（值不值）？
- 你打算把这套机制搬到公众号生产线上吗？（这是天然的下一篇钩子）

### 首选 3｜S10《AI 说"我刚查过了"，然后写了一个不存在的版本号》

**为什么是它**：最短、最锐、共鸣最强。它不需要架构背景，任何一个用 AI 写过 `package.json` 的人都被咬过。而且它给出一条可执行的纪律，不是情绪宣泄。适合做"破圈"的第一篇或第二篇。

**叙事骨架**：

1. 场景：让 agent 初始化一个 LangChain 学习工程，它写了一份 `package.json`。
2. 事故：里面写着 `typescript@^5.9.4`。这个版本不存在，5.x 最高是 5.9.3。
3. 更麻烦的不是写错，是它**声称**"刚从 registry 查的实时值"。我去核，才发现这句是编的。
4. 暴露方式：用户跑 `pnpm install`，`ERR_PNPM_NO_MATCHING_VERSION`。
5. 于是立规则：任何要落盘的版本号，必须当场查 registry 的 `versions` / 包的 `engines`；没核实的必须显式标注"未核实"，绝不许写成"我查过了"。
6. **延伸（这才是高阶部分）**：这条规则后来救了更多次 —— 顺带查出 TypeScript 5.x 的真实上限、`@langchain/core` 是 `langchain` 的 peerDependency 而不在 dependencies（所以官方安装命令必须显式写两个包）、以及"构造模型对象 ≠ 发请求"（用一把故意写错的 key 调 `initChatModel` 照样成功，报 401 的是紧接的 `invoke`）。
7. **结论**：模型对"我验证过"的自述，和它对代码的自述一样不可信。可信的只有当场跑出来的输出。

**需要作者补的口述素材**：

- 你发现它是编的那一刻，第一反应是什么？有没有一瞬间觉得"它连这个都敢编，那之前的东西还能信吗"？
- 之后你怎么改自己的工作流？（是每步都验，还是只验"会落盘的"）
- 有没有一次你**没**验，后来出事了？（如果有，这篇会更有分量）
- 这条规则执行两个月后，验的成本降下来了吗？

### 对照组（不在这三个里，但值得知道）

**S7《登录切不了账号》** 是唯一一个纯前端、零 AI 的候选。它的价值是**测受众**：如果账号起来靠的是 AI 题材，S7 会告诉你读者到底是谁。建议排在系列 A 的第 3–4 篇之后发，不要作为第一篇——开号第一篇必须是"AI 协作"主题，否则人设立不住。
